# 설계 문서

## 1. 설계 목표

Rust 문서 생성기로 최초 문서를 만들고, 생성된 단일 HTML 파일 하나가 **보고서(결과물)이자 편집기**가 되게 한다. 생성 이후에는 서버·설치·네트워크 없이 문서를 열고, 편집하고, 전달하고, 다시 편집한다.

## 2. 핵심 패턴 — 자기 편집 문서 (Self-Editing Document)

문서가 자기 자신을 편집·재생성한다. 파일 하나가 세 가지를 모두 품는다.

```
┌────────────────── report.html ──────────────────┐
│  ① 데이터    <script type="application/json">     │  ← 편집 대상
│  ② 렌더러    바(bar)·타임라인·표를 그리는 JS       │  ← 편집 도구
│  ③ 에디터    드래그·표 입력·추가/삭제 JS           │  ← 편집 도구
│  ④ 재조립    현재 상태로 ①을 갱신해 파일 재생성     │  ← 영속화
└──────────────────────────────────────────────────┘
```

동작 흐름:

1. **로드**: 스크립트가 `#gantt-data`의 JSON을 읽어 메모리 상태(`state`)로 파싱하고 화면을 그린다.
2. **편집**: 사용자의 드래그·표 입력이 `state`를 변경하고 화면을 다시 그린다. 파일은 아직 안 바뀐다.
3. **저장**: `state`를 `#gantt-data`에 다시 써넣고, 렌더링 결과를 비운 뒤 `document.documentElement.outerHTML`을 직렬화해 완전한 HTML로 저장한다.
4. **재개**: 저장된 파일을 열면 다시 1번부터 — 무한 왕복.

### 왜 렌더 결과를 비우고 저장하나
`outerHTML` 직렬화는 현재 DOM을 그대로 담는다. 렌더된 막대·그리드·편집표 같은 **전이 상태**가 파일에 박히면, 다시 열 때 스크립트가 또 그려 중복되거나 편집모드 클래스가 남는다. 그래서 저장 직전에:

- 편집모드를 끄고(보기 상태로 정규화),
- 렌더 컨테이너(사이드바·타임라인·편집표)를 비우고,
- 직렬화한 뒤,
- 원래 화면을 복구한다.

결과 파일은 항상 "빈 캔버스 + 데이터 + 코드" 상태 → 열릴 때 스크립트가 깨끗하게 새로 그린다.

## 3. 최초 문서 생성기와 Markdown 블록

현재 프로토타입은 브라우저에서 기존 HTML을 열어 편집하는 것만 가능하고, 최초 문서를 생성하는 진입점이 없다. 이를 해결하기 위해 Rust 기반 PAGE 문서 생성기를 별도 도구로 둔다.

생성기는 Markdown 파일을 입력으로 받는다. 일반 Markdown은 문서 본문으로 사용하고, fenced code block의 언어 식별자를 통해 PAGE 문서 유형과 데이터를 구분한다.

지원 블록은 다음과 같다.

| 블록 | 역할 | 처리 방식 |
|------|------|----------|
| page:gantt | 편집 가능한 간트차트 | PAGE 간트 데이터 모델로 변환 |
| page:chart | 데이터 시각화 | 차트 종류·데이터·옵션 모델로 변환 |
| page:report | 구조화된 일반 보고서 | 섹션·문단·표 모델로 변환 |
| mermaid | 플로우차트·UML 등 호환 다이어그램 | PAGE 모델 또는 정적 렌더링으로 변환 |

Mermaid는 PAGE 전용 문법으로 복제하지 않는다. Mermaid의 gantt, flowchart, classDiagram, sequenceDiagram 등은 호환 입력으로 지원하되, PAGE에서 직접 편집해야 하는 유형은 page:* 모델을 우선 사용한다. 구조적으로 변환할 수 없는 Mermaid 유형은 정적 SVG 등으로 렌더링할 수 있다.

생성 흐름은 다음과 같다.

    Markdown → Rust Markdown Parser → PAGE Intermediate Model → 단일 PAGE HTML
                                                                  ↓
                                                   브라우저에서 보기·편집·재저장

PAGE 중간 모델은 생성기와 브라우저 런타임 사이의 계약이다. 예를 들어 page:gantt는 title과 tasks[] 모델로 변환되어야 하며, 생성된 HTML은 이 모델을 기반으로 막대 이동·기간 조절·표 편집·재저장을 제공한다.

구체적인 블록 내부 문법과 CLI 옵션은 생성기 구현 단계에서 확정한다. 입력은 Markdown 파일 하나, 출력은 PAGE 단일 HTML이라는 계약을 유지한다. Rust 생성기는 최초 생성 단계에서만 필요하다.

## 4. 저장 전략 (요구 2·4의 핵심)

`file://` 페이지는 서버가 없어 저장 경로가 두 갈래다. **기능 탐지 후 폴백**한다.

| 순위 | 방법 | 지원 | UX |
|------|------|------|-----|
| 1 | File System Access API (`showSaveFilePicker`) | Chrome/Edge | **같은 파일 덮어쓰기** |
| 2 | `Blob` + `<a download>` | 모든 브라우저 | 새 파일 다운로드 |

```js
if (window.showSaveFilePicker) {
  try { /* 파일 핸들에 직접 쓰기 */ return; }
  catch (e) { if (e.name === 'AbortError') return; /* 아니면 폴백 */ }
}
/* Blob 다운로드 폴백 */
```

- localStorage는 `file://` 오리진에서 불안정 → 1차 저장 수단으로 쓰지 않는다(선택적 자동복구 백업 용도로만 고려).
- 사용자가 대화상자를 취소(`AbortError`)하면 조용히 중단, 그 외 오류는 다운로드로 폴백.

## 5. PDF 출력 (요구 5)

브라우저의 인쇄 → "PDF로 저장"을 사용한다. 별도 PDF 라이브러리 없음(의존성 0 유지).

- `@media print`로 툴바·편집표·리사이즈 핸들 숨김.
- `@page { size: landscape }`로 가로 출력.
- `print-color-adjust: exact`로 막대 색·주말 음영 유지.
- `break-inside: avoid`로 막대·행 잘림 방지.
- **한계/로드맵**: 몇 달짜리 긴 일정은 한 페이지에 다 안 들어감. 축소 스케일 또는 주/월 단위 페이지 분할 로직 필요(§8).

## 6. 데이터 모델

```jsonc
{
  "title": "샘플 프로젝트 일정",
  "tasks": [
    {
      "id": "t1",              // 고유 식별자
      "name": "요구사항 분석",
      "start": "2026-07-06",   // YYYY-MM-DD (포함)
      "end":   "2026-07-10",   // YYYY-MM-DD (포함)
      "progress": 100,          // 0~100
      "color": "#4f7cff"
    }
  ]
}
```

- 날짜는 **UTC 자정 기준**으로 파싱해 타임존 영향을 제거한다(`Date.UTC`).
- `end`는 **포함**(inclusive) — 막대 폭 = (종료−시작+1)일.
- 스키마 확장 시 하위 호환: 알 수 없는 필드는 보존, 없는 필드는 기본값.

## 7. 렌더링 구조

SVG 대신 **HTML/CSS 절대배치**를 택했다 — 드래그·인라인 편집·인쇄에 더 유리하고 유지보수가 쉽다.

```
.gantt
├── .sidebar        태스크명 (고정 좌측)
│   ├── .sb-head
│   └── .sb-row × N
└── .timeline       가로 스크롤
    └── .tl-inner (width = 전체 일수 × 하루폭)
        ├── .tl-head    월 행 + 일 행 (sticky)
        └── .tl-body
            ├── .col-we      주말 음영
            ├── .rowline × N 행 구분선
            ├── .today-line  오늘 표시
            └── .bar × N     막대(진행률 fill + 라벨 + 좌우 핸들)
```

- 사이드바와 타임라인의 **행 높이(`--rowh`)를 CSS 변수로 공유**해 정렬을 맞춘다.
- 좌표 = 일수 × `--dayw`. 모든 치수는 CSS 변수(`--dayw/--rowh/--headh/--sidew`)로 조정.

## 8. 상호작용 설계

- **드래그(이동)**: 막대 본체 mousedown → 픽셀 이동량을 일수로 스냅 → `start/end` 동시 이동.
- **리사이즈**: 좌/우 핸들 → `start` 또는 `end`만 변경(`start ≤ end` 보장).
- **양방향 동기화**: 드래그가 표의 날짜 입력을 갱신(`syncRow`), 표 입력이 막대를 갱신. 포커스 유지를 위해 텍스트 입력은 전체 재렌더 대신 부분 갱신.
- **경계 케이스**: 리사이즈로 start가 end를 넘지 않게 clamp.

## 9. 로드맵 (미구현)

우선순위 순.

1. **PDF 페이지 분할/스케일** — 긴 일정 대응(§4 한계 해소).
2. **의존관계(선행/후행) 화살표** + **마일스톤**(다이아몬드 마커).
3. **Undo/Redo** — `state` 스냅샷 스택.
4. **태스크 그룹/섹션** — 접기, 요약 막대.
5. **가져오기** — CSV/JSON 붙여넣기로 대량 입력.
6. **보고서 유형 확장** — 간트 외(타임라인, 칸반 스냅샷 등). 자기 편집 문서 골격(§2·§3)은 유형과 무관하게 재사용.

## 10. 코드 구성 (현재)

단일 파일 `src/gantt.html`. 논리 구획:

| 구획 | 역할 |
|------|------|
| `<script id="gantt-data">` | 편집 대상 데이터 |
| `<style>` | 화면 스타일 + `@media print` |
| 날짜 유틸 | UTC 파싱·포맷·일수 차이 |
| `render/renderChart/renderTable` | 상태 → DOM |
| `attachDrag/syncRow` | 드래그·리사이즈·동기화 |
| 편집표/추가/삭제/제목 핸들러 | 입력 → 상태 |
| `setEdit` | 모드 전환 |
| `save` | 자기 재조립 + 저장 폴백 |

향후 규모가 커지면 빌드 단계에서 **여러 소스 파일을 단일 HTML로 인라인 번들**하는 방식으로 분리하되, **배포 산출물은 항상 단일 파일**이라는 불변식을 유지한다.
